# Feature Overview

This is the extensible feature roadmap for the Twilight: 2000 Fourth Edition GM tool. Keep unimplemented capabilities marked as planned; do not describe roadmap items as available until they are implemented and verified.

## Status Key

- **Prototype**: Interactive groundwork exists, but it is limited and may use sample data or bookkeeping rather than a complete subsystem.
- **Partial**: Some requested behavior exists, but important workflows remain unimplemented.
- **Planned**: Not implemented yet.

## Product Surfaces

Campaign Setup and the GM runtime retain separate GM-only pages with cross-tool links. Initial browser-local drafts move into play through **Save setup to server**, optional **Download saved JSON**, and the runtime's **Import setup package** preview/confirmation. The import interaction is isolated from live desk controls; runtime changes never synchronize back into the authoring draft. This separation does not change the prototype/partial status of either surface.

**Server setup saves:** Authenticated GMs save validated setup JSON under the service's app-root `gmpack/campsetups/<normalized-campaign>-<save-id>-setup-v2.json`. Static images are copied to `data/maps/<normalized-campaign>/<asset-id>.image` with their ownership/format/dimensions JSON sidecars. The saved package references that copied asset, not a client-supplied filesystem path. Each save creates a new version with new IDs and does not overwrite earlier saves or source uploads. Server packages can be reopened with validation/replace-draft confirmation or downloaded for runtime import; read access is restricted to their owning GM. Saving alone does not import or publish a campaign. Existing geographic and PMTiles package formats remain compatible. Packages, images, and sidecars are ignored by source control and must be transferred together for cross-host use.

- **Campaign Setup Tool** — Prototype. A standalone GM-only authoring page uses Brief → Base map → Terrain Grid → Locations → Settlements → Factions → Scenario Notes. New setups default to the online MapTiler map; the GM defines geographic extent by clicking two opposite corners on the loaded map. The selected rectangle is shown and can be reset/reselected; the current viewport is not used as campaign bounds. Internet and a session-only, GM-supplied API key are required; the key is never saved in a draft or package. MapTiler's built-in attribution remains visible, so this mode has no separate manual attribution field. A static image is optional and uses a GM-entered width in kilometres, validated pixel dimensions, explicit `image-km` extent, and x/y kilometre positions. Static-image attribution remains required. New Atlas GeoJSON authoring is removed; existing geographic and PMTiles packages remain import-compatible. Numeric bounds entry and draggable corner handles are not provided. Terrain assignments use 10 km axial Q/R travel hexes anchored to the map's top-left corner and support batch assignment. Each faction has an independent overlapping Q/R influence layer; settlements retain explicit GM-controlled faction prominence order. These are campaign labels, not rules modifiers. The editor displays the T2K Referee Aid / Strategic Play terrain table as reference only. Locations default to GM-only and can be marked player-eligible; this never publishes them, and linked settlements inherit visibility. Drafts autosave locally, validate/preview/export schema-v2 setup JSON, and reopen validated packages after explicit replacement confirmation. Static-image/PMTiles assets and sidecars in `data/maps/atlas/` transfer separately; images require attribution and new PMTiles need an HTTPS license URL. Rights remain GM-verified. MapTiler setup and runtime maps require internet; public OSM tiles are not bulk-downloaded. Validated packages import into GM-owned SQLite runtime campaigns with faction layers and prominence preserved. The GM separately publishes selected text and map layers; broader shared gameplay remains planned.
- **Settlement generator** — Prototype. In Campaign Setup, choose a location marked Settlement and generate editable GM-defined scale (including Camp), security, attitude, leadership, and situation descriptors. Settlement name, map position, and Q/R reference come from the Locations editor; population is a manual GM estimate. The [de-fenestra.com reference generator](http://www.de-fenestra.com/t2k/settlement_generator_strict.html) explicitly uses Twilight: 2000 v2.2 rules, so its rules tables and formulas are not used as Fourth Edition mechanics. Generated descriptors are scenario aids and are not represented as official rules.
- **GM Tool** — Partial. Supported records, conditions, inventories/proposals, publications, COMMS, route stops, location coordinates, and GM audit metadata persist in SQLite. Runtime route/map edits use owner/revision checks, append audit events, and participate in backup recovery without changing the setup source or existing player publication. Cross-host runtime backup import creates a new local campaign and requires explicit mappings to active, unassigned local player accounts; credentials and sessions are never imported. New setup imports atomically initialize a runtime dashboard and route at the declared starting location, then automatically select and load that campaign. A versioned, GM-only roll-table catalog is shared across GM accounts and campaigns, supports validated JSON import/export, and rolls only after an explicit click without changing campaign state. The GM must review the labeled bookkeeping baseline: 2000-01-01 00:00, day 0, zero distance/supplies, and weather Not recorded. Previously imported campaigns with missing dashboards are not retroactively repaired. Broader action coverage, rules automation, content snapshots, map editor polish, and offline-asset portability remain open. Scheduled backups are now implemented (see Operational Reliability below). HTTP is for a trusted LAN only.
- **Player Interface** — Partial. All five handset views are connected. Character includes read-only GM condition values for the active assigned character; private GM notes and other characters' records are excluded. Unset values remain Not recorded rather than implying healthy/zero. Views refresh on opening/Refresh/return and every 15 seconds while visible. Inventory changes require GM approval. Condition/carrying effects and dice-governed actions remain GM-managed.
- **GM-managed player report** — Implemented text-only slice. Save draft, server preview, explicit publish, and withdraw use SQLite with owner/revision checks. Editing a draft does not alter the current published copy. API, persistence/recovery, and synthetic GM/player browser checks pass. Structured report sections, media, and publication history remain planned.
- **Player data boundaries** — Implemented current-slice checks. Active campaign/character assignment controls inventory reads and proposals; player payloads cannot select another character or directly change accepted items. GM ownership, item revisions, source confirmation, and current submitter assignment control approval. Proposal history is filtered by submitting account for player reads. Other players' inventory, private submissions, GM notes, and account records are excluded.

## Map Foundations

- **Static image background** — Setup supports GM-provided PNG, JPEG, or WebP (50 MiB limit): select Static image, enter the full image width in kilometres, upload, then continue with terrain, locations, and setup-package export. Validated dimensions determine height; explicit `image-km` extent and `{x,y}` kilometre positions preserve the 10 km grid without fabricated latitude/longitude. Scale correctness remains GM-verified. Existing geographic image packages retain their geographic interpretation. Runtime import, location/route editing, map publication, and backups retain the declared coordinate space; incompatible online/PMTiles replacements are not available for image-coordinate campaigns. Publication remains explicit and unchanged by draft edits. Players retain read-only pan/zoom up to 200% and reset to the GM-set position. Images require attribution; an HTTPS license link is optional for GM-owned images. Anything drawn into a published image is visible: there is no fog masking. Local authenticated asset routes serve images without online tiles; binary `.image` files and JSON sidecars transfer separately.
- **Campaign extent** — Partial. Manual numeric bounds and draggable corner handles remain removed. New geographic campaigns use two opposite MapTiler map clicks; the corners are normalized into validated geographic bounds, displayed as a rectangle, and can be reset/reselected. Image extent comes from validated dimensions and GM-entered width. Existing geographic/PMTiles package coordinates remain supported. Authoritative location and published-geometry validation uses the declared coordinate space. Broader extent/scale editing remains planned; replacement images must retain scale/aspect ratio when map data already exists.
- **Published geometry** — Implemented API and GM editor slice. The publication boundary accepts bounded labeled LineString and single-ring Polygon markings alongside points. Browser smoke testing verified GM save, preview, publication, and Player Interface rendering on the OSM fallback.
- **Offline basemap** — Partial. The GM can upload raster or MVT vector PMTiles v3 archives (50 MiB limit); vector archives use a basic local MapLibre style. Setup packages/runtime preserve the format, required attribution, and HTTPS license URL, and the player map displays the credit and terms link. The server serves byte ranges from `data/maps/atlas/`. Archives and JSON sidecars are local-only and must be transferred separately; a real licensed archive has not yet been verified end to end. The tool does not verify license permissions.
- **Future map work** — Rich vector styling, vertex-drag editing, geometry history, fog masking, and rules-based travel calculations remain planned.

## Combat System

- **Ranged combat calculator** — Implemented. Resolves small arms attacks using Agility + Ranged Combat skill, applies range modifiers, calculates damage with strength bonus and armor reduction, detects weapon jams (magazine-fed only), and tracks ammo consumption. All mechanics verified against T2K 4E core rules.
- **Close combat calculator** — Implemented. Resolves melee attacks using Strength + Close Combat skill, applies strength bonus to damage, and detects critical hits. Backward compatible with existing combat system.
- **Grenade throw calculator** — Implemented. Resolves grenade attacks using Agility + Mobility skill with blast radius calculation for fragmentation grenades and adjacent hex damage. Supports scatter calculation for missed grenades.
- **Heavy weapons system** — Implemented. Extends combat calculator with fragmentation and shaped charge grenades (double armor penetration), anti-personnel and anti-vehicle mines, and blast mechanics. Fragmentation grenades affect 7 hexes (primary + 6 adjacent); shaped charges and mines affect 1 hex only. Armor reduction differs by weapon type (normal vs. ×2 against shaped charges).
- **Vehicle combat system** — Implemented. Resolves vehicle targeting attacks using Agility + Ranged Combat skill, applies weapon penetration against vehicle structure value, supports standard and vulnerable spot targeting (×2 penetration), and determines damage effects based on penetration margin: immobilized (margin 1-2), destroyed (margin ≥3), or glanced-off (no penetration).
- **Combat logging** — Implemented. Records all combat results (ranged, close combat, grenades, heavy weapons, vehicles) in campaign audit log with attacker, target, weapon, rolls, damage, and outcomes. Stores complete roll breakdown and outcome for GM review and after-action analysis.
- **GM combat interface** — Implemented. Web-based `/combat.html` form with tabbed interface for ranged, close combat, grenade, heavy weapon, and vehicle combat. Provides input validation, real-time result calculation, and narrative outcome display. Results automatically logged to campaign audit trail.
- **Combat result recording** — Implemented. All combat resolutions linked to campaign audit trail with character attribution, game date/time stamps, and complete roll history. Combat log is searchable by combat type, attacker character, and date range.
- **Combat result publishing** — Planned. Results can be published to players via situation report; GM controls what combat outcome information is visible to players.

## Game Master Features

- **Runtime route and map editing** — Partial. The route editor contains the campaign map and its existing 10 km axial overlay. Clicking a visible hex stages its center as the next waypoint; an existing center location is reused, otherwise Save route atomically creates a GM-only waypoint location. In Player Map publication, point markings and player position are placed by selecting a visible campaign hex; bounded center coordinates remain in the existing draft/API model. Geographic and static-image coordinate modes share the same grid conversion. Manual location selection, route order, details, distances and removal remain available; distances are GM-entered, not travel-rule calculations. Cancel discards staged hex selections. Saves are owner/revision checked, audited, and backed up without moving the recorded party position, changing the setup source, or publishing a player map. Location coordinates remain editable; broader map editing is planned.
- **Personnel roster editing** — Partial. The GM can create personnel from Fourth Edition NPC archetypes, customize name/role/condition/readiness, edit attributes, and remove records through the owner-scoped runtime API. The archetype browser groups available templates, and saves use the campaign revision; stale edits reload current roster state while preserving the open draft for review and retry. Runtime backups preserve personnel fields. Bulk operations, broader roster history, and derived rules effects remain unimplemented.
- **Campaign audit history** — Implemented metadata slice. Owner-only Audit view shows actor/target snapshots, record and campaign revisions, UTC time, campaign date/day, and live/recovered origin with pagination. Condition save/clear, inventory stock/correction/removal and proposal decisions, report/map draft/publish/withdraw, manual dashboard and journal updates, faction creation/influence/prominence edits, character change request reviews, player seat assignments, and restores are audited in their mutation transactions. Failed writes and read-only previews create no events. SQLite rejects event updates/deletes; backup restore preserves later live entries, merges missing saved events as backup-origin metadata, rejects conflicting IDs, and appends a restore event. API permissions, atomic failures, file reopen, recovery, and browser paging/safe-text/player denial checks pass. This is not a cryptographic tamper-proof log. Player proposals/COMMS and account/auth events are not audited by this slice; full snapshots, retention tooling, and wider coverage remain planned. Historical pre-upgrade actions are not fabricated or backfilled.

- **Development runtime fixture** — Implemented for development/testing only. `node server/seed-sample.cjs --db <dev-db-path> --gm <gm-username>` creates an idempotent `The Long Road` campaign with dashboard counters, route stops, personnel, journal entries, and one sample player seed. It refuses the configured/default live DB. The owning GM can read the normalized snapshot from `GET /api/campaigns/:id/runtime`; supported Situation, Personnel, Movement, and Journal fields, including campaign era/premise display, connect to it. Remaining dashboard panels are still incomplete.
- **Player seed authoring** — Partial. The GM-only Player Seeds page stores server-backed templates independently of campaigns, creates player accounts with a one-time temporary password and enforced password change at first login, records T2K 4E attributes, skills, CUF, and structured manual life-path outcomes, and assigns a copy to a selected campaign on explicit GM action. Unassigned players see no campaigns. Template edits do not mutate assigned campaign characters; templates with active assignments cannot be deleted. Browser-only drafts remain untouched and can be downloaded, but are not automatically migrated. Life-path rules are recorded manually and are not automated or validated.
- **Scheduled event system** — Planned.
- **Campaign clock control** — Implemented GM bookkeeping slice. +6h advances stored date/time by six hours; date/day increment only at midnight. Once per date, reaching/crossing 12:00 consumes one shared ration-day, clamped at zero, with a daily usage marker and atomic journal/audit records. This GM-defined schedule is not a verified Fourth Edition consumption procedure. Fuel and personal items remain manual. Existing clocks initialize at 00:00; historical message/audit times remain unknown. Clock and supply usage recover together; replaying a processed date cannot charge twice. General event resolution remains planned.
- **Weather control** — Partial. The GM can select Fair, Cloudy, Rain/Snow, or a GM-defined condition and record a physical d6 result with the matching Referee Aid symbol outcome. No numeric face mapping is assumed. The owner- and revision-checked runtime API applies the one-step change, limits rolls to one per shift, audits and journals results, and backs up the roll state. Rain/Snow returns to Cloudy after one Fieldbook shift and enforces a full Cloudy shift before another roll. Effects remain GM-adjudicated; weather does not modify character or attack rolls.

## Environment

- **Dynamic weather** — Implemented. Fair/Cloudy/Rain-Snow state progression with die roll interpretation (0 symbols = no change, 1 = worsen, 2 = improve). Auto-revert: Rain/Snow reverts to Cloudy after 1 shift. Visibility modifiers by condition and light level (daylight/darkness/moon). Attack/march/drive modifiers apply: Rain/Snow -1 attack, -1 march, -2 drive. GM interface at `/weather.html` with 6 calculator panels. Full T2K 4E rules verified against Referee Aid - Strategic Play.
- **Travel calculations** — Implemented. Marching distances (2 hexes/shift road/open, 1 hex/shift other terrain). Driving distances (base 5 hexes/shift with terrain multipliers: road/open ×1, woods ×0.5, hills ×0.75, mountains ×0.25, lake ×1, swamp ×0.5, ruins ×0.5). Fuel consumption (1 liter per hex, alcohol ×2). Rations calculator (1 per person per day, separate food/water). Terrain modifiers for Foraging/Hunting/Scrounging/Driving tasks across all 8 terrain types. Encounter distance (halfway point in shift). GM-facing calculator and HTTP API. All mechanics verified against Referee Aid - Strategic Play.
- **Supply & conditions** — Implemented. Starvation effects (cannot heal, -1/week, dies week 3). Dehydration effects (cannot heal, -1/day, dies day 3). Sleep deprivation effects (cannot heal stress, -1/day). Hypothermia mechanics (Stamina roll in cold, GM-adjudicated frequency). Status tracking per person/group. Integrated with travel system.
- **Route modifiers** — Planned. Weather and terrain modifiers are implemented; scenario-specific conditions and strategic campaign modifiers remain planned.
- **Travel conditions** — Implemented. Full travel system supports weather, terrain, fuel, supply, and affliction tracking. Campaign-specific event conditions remain GM-managed.

## Operational Reliability

- **Campaign backup and restore** — Implemented. Atomic backup API exports complete campaign state; restore replaces campaign atomically with rollback capability. Backup versioning and history with unique timestamps. Cross-host import creates new campaign with explicit player account mapping. Credentials and sessions not imported.
- **Scheduled backup automation** — Implemented (Phases 1-2). 5 schedule types: disabled, hourly, every-6-hours, daily (2:00 AM UTC), custom-interval. Retention policies by age (days) and count (max backups). HTTP API endpoints for schedule management (GET, POST, PATCH) and history retrieval (paginated). Database schema with automatic initialization and dedicated regression tests. Broader deployment and recovery acceptance must be verified separately; this status is not a production-readiness certification.
- **Automatic backup recording** — Implemented (Phase 3). Event-triggered backups on combat resolution, journal entries, inventory changes, and character change approvals. Background task runner with 1-minute check interval for scheduled backups. Simple three-level event labeling (manual, scheduled, event). Mutation capture hooks for integration with campaign mutations and dedicated automation regressions. Historical phase verification figures are retained in the dated completion reports; use a current run for the whole-suite result.
- **Backup HTTP API** — Implemented. Four endpoints for campaign backup management: GET /api/campaigns/:id/backup-schedule, POST /api/campaigns/:id/backup-schedule, PATCH /api/campaigns/:id/backup-schedule, GET /api/campaigns/:id/backup-history. All endpoints require GM authentication and support owner-scoped access. Standard HTTP error codes (400, 404, 422) with error messages.
- **PMTiles asset serving** — Partial. The GM can upload raster or MVT vector PMTiles v3 archives (50 MiB limit); the server detects tile type and serves byte ranges. Vector archives use a basic local MapLibre style. Setup metadata requires attribution and an HTTPS license URL for new uploads and publishes both to players; license rights are not verified automatically. Files and JSON sidecars live under `data/maps/atlas/` and are not embedded in JSON or runtime backups. No real licensed archive was available to verify tile decoding/rendering.
- **Graceful error handling** — Partial. Backup/restore operations handle errors atomically; background runners use graceful degradation with console logging; broader error recovery and conflict resolution remain planned.
- **Cross-host recovery** — Partial. Runtime backup import creates new campaign; full asset portability and recovery remain planned.

Campaign setup, session-level publishing, strategic play weather/movement, and character creation fully match official rules. Indices optimize common queries (relationships by faction, events by date/type, threats by status/level).

- **GM UI** — Planned. Modal interfaces for faction roster (list, add, edit, delete, relationship matrix view), threat tracker (priority list, severity coloring, status updates), territory annotations on map, and event log viewer.

**Design Notes:** No automation or rule mechanics applied. All entries are GM-managed and manually entered. Factions, threats, and events are campaign-scoped and isolated.
